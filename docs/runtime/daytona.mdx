title: Daytona Runtime
description: Run agents in Daytona Cloud sandboxes
---

Xum can run workspaces in [Daytona](https://www.daytona.io/docs) sandboxes. Each new Daytona workspace gets its own sandbox, and Xum connects to it over SSH through Daytona's SSH gateway. Builds, tests, and other agent commands use the sandbox's CPU and memory, not your machine's. Under the hood a Daytona workspace is an [SSH workspace](/runtime/ssh), so `XUM_RUNTIME` is `ssh`.

## Requirements

- A Daytona account and an API key from the Daytona dashboard
- `ssh` installed on the machine running Xum
- A snapshot (or Daytona's default) with git and your toolchain

## Set up access

1. Open **Settings > Runtimes** and find the **Daytona** row.
2. Paste your API key and click **Save**. Change **API URL** only for a self-hosted (BYOC) Daytona install. **Target** picks a region; leave it empty for Daytona's default.
3. Click **Test connection**.

Xum stores the key in `~/.xum/daytona.json` (under `XUM_ROOT` when it is set) with file mode `0600`. The settings page never shows a saved key again: to change it, enter a new one, or click **Remove key**.

Without a saved key, Xum uses `DAYTONA_API_KEY` and `DAYTONA_API_URL` from its own environment. A saved key wins over the environment.

<Warning>
  Do not put your Daytona API key in **Secrets**. Xum passes secrets to agent turns and terminals,
  so an agent could read the key and create or delete sandboxes in your organization.
</Warning>

## Project defaults

In **Settings > Runtimes**, change the scope from **All** to a project and turn on **Override project settings** to set the project's default **Snapshot** and **Size** for new Daytona workspaces. The new-workspace controls start from these values.

| Size   | vCPU | Memory | Disk   |
| ------ | ---- | ------ | ------ |
| Small  | 2    | 4 GiB  | 10 GiB |
| Medium | 4    | 8 GiB  | 20 GiB |
| Large  | 8    | 16 GiB | 40 GiB |

Small is the default. Xum offers only these sizes, which keeps costs predictable.

## Create a workspace

1. In the new-workspace controls, choose **Daytona** as the runtime.
2. Select **New**, then pick a snapshot and a size.
3. Xum creates the sandbox, waits until it starts, copies your user-level [tool hooks](/hooks/tools) and skills into it, clones the project, and runs the [init hook](/hooks/init).

Xum labels each sandbox it creates with `xum.instance`, `xum.workspaceId`, and `xum.project`. If Daytona rejects the size for a snapshot, Xum creates the sandbox at the snapshot's size and then resizes it.

## Use an existing sandbox

Select **Existing** and pick a sandbox from your organization. Xum treats an attached sandbox as yours: it never copies files into its home directory, stops it, or deletes it. It does start the sandbox when a workspace needs it. Several Xum workspaces can share one sandbox; each gets its own directory.

## Lifecycle

| Xum event                           | Daytona action                                                                                |
| ----------------------------------- | --------------------------------------------------------------------------------------------- |
| A turn starts                       | Start the sandbox if it is stopped or archived (waits up to 3 minutes)                        |
| An agent is streaming or a job runs | Report activity every minute, so Daytona does not stop the sandbox                            |
| Idle                                | Daytona stops the sandbox after 30 minutes and archives it after 1 day stopped                |
| Sub-agent with a forked workspace   | A new worktree in the same sandbox, not a second sandbox                                      |
| Archive                             | Follows **Settings > General > Remote box on archive** (default: stop)                        |
| Delete                              | Check for uncommitted or unpushed work, then delete the sandbox (attached sandboxes are kept) |
| Opening a workspace                 | Background git and PR status checks do not start the sandbox; they wait until it runs         |
| Sandbox deleted outside Xum         | The workspace reports that the sandbox no longer exists; Xum does not recreate it             |

A sandbox Xum created can serve several workspaces when you fork one. Xum deletes it only with the last of them, archived ones included; deleting any other one removes its worktree and keeps the sandbox. Archive does not stop or delete a sandbox that another workspace still uses. When you delete the last workspaces on a sandbox at the same time, Xum deletes the sandbox once, after the last of them passes its check for uncommitted work.

If the sandbox is still being destroyed (for example after a failed setup), delete waits up to a minute for Daytona to finish. A forced delete removes the workspace even when Daytona refuses to delete the sandbox; it then shows a warning that names the sandbox, which you delete in the Daytona dashboard.

With **Remote box on archive** set to delete, Xum first checks the workspace for uncommitted or unpushed work. If it finds some, or cannot run the check, it stops the sandbox instead and shows a warning.

Once a minute, Xum also stops running sandboxes that carry this install's label but that no workspace uses. It never deletes them.

## SSH setup

Xum writes the SSH settings for its sandboxes to `~/.xum/ssh/daytona.conf` and adds a managed block to the end of `~/.ssh/config` that includes it for hosts named `<sandbox-id>.xum--daytona`. The gateway's access token is the SSH user name; Xum keeps it in memory and refreshes it before it expires. It revokes the token when it replaces it, when you change the Daytona settings, and when it deletes or releases the sandbox. At startup, Xum reads the tokens that an earlier run left in `daytona.conf`, so it can filter and revoke them too. When the gateway refuses a token (for example one revoked outside Xum), Xum gets a new one and runs the command again once. Xum replaces any token it finds in SSH errors and logs with `<daytona-token>`; output of commands that you or an agent run in a terminal is not filtered.

Xum pins the gateway's host keys in `~/.xum/ssh/daytona_known_hosts` and refuses a gateway whose key does not match, with OpenSSH and with the built-in SSH2 transport alike. This holds for `xum server` too, which otherwise skips host key checks for SSH hosts.

OpenSSH uses the first value it finds for each setting. If your `~/.ssh/config` has a `Host *` entry with a `User` or `UserKnownHostsFile` line above Xum's block, connections to sandboxes fail. Xum checks for this and reports it; move the line into a narrower `Host` entry, or below Xum's block. A `StrictHostKeyChecking` line there has no effect: Xum always runs `ssh` with strict host key checking for sandboxes.

## Notes

- **Costs:** Daytona bills running sandboxes by size and time. Archive or delete workspaces you no longer need, and pick the smallest size that works.
- **CPU count:** `nproc` inside a sandbox reports the host's CPUs, not the sandbox's, so builds may start too many parallel jobs. Set job counts (for example `MAKEFLAGS=-j4`) in your snapshot or in the project's [`.xum/tool_env`](/hooks/tools).
- User-level hooks and skills in a sandbox live under `~/.mux`, the same as on other SSH hosts.
