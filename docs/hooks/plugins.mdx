<Note>Plugin hooks are experimental. Expect breaking changes while we iterate.</Note>

An [Agent Plugin](/agents/agent-skills#agent-plugins) can ship hooks in three formats:

| Format        | File                                                      | Runs as                                         | Trust step                        |
| ------------- | --------------------------------------------------------- | ----------------------------------------------- | --------------------------------- |
| Codex format  | `hooks/hooks.json`                                        | A call to a tool on the plugin's own MCP server | You trust each hook in Settings   |
| Cursor format | `hooks/hooks.json` of a Cursor plugin, or its `hooks` key | A shell command on the Xum host                 | You trust each hook in Settings   |
| Xum-native    | `hooks.js` in the plugin root                             | JavaScript in a QuickJS sandbox                 | Project Trust for project plugins |

A [Claude Code plugin](/agents/agent-skills#claude-code-plugins) ships `hooks/hooks.json` too. Xum lists those hooks and never runs them. See [Claude Code plugin hooks](#claude-code-plugin-hooks). In a [Cursor plugin](/agents/agent-skills#cursor-plugins), Xum reads `hooks/hooks.json` in the Cursor format only. See [Cursor hooks](#cursor-hooks).

For hooks in your own repository, use [tool hooks](/hooks/tools) instead.

## Codex-format hooks

Xum reads the [Codex CLI hooks format](https://learn.chatgpt.com/docs/hooks), so a Codex plugin's `hooks.json` works without edits.

### Where they come from

Xum reads `hooks/hooks.json` in the plugin. If `plugin.json` has `extensions["com.openai"].hooks`, that list replaces the default file. Each entry is a relative path to a hooks file or an inline hooks object. An empty list turns the default file off.

Only managed plugins run these hooks. A managed plugin is one you installed from **Settings → Plugins** into `~/.xum/plugins`. Project plugins and plugins in `~/.agents/plugins` never run them.

Xum also runs no Codex-format hook in these cases:

- The project is not trusted.
- The workspace is not a local or worktree workspace, for example an SSH, Docker, devcontainer, or Coder workspace.
- The workspace is a multi-project workspace.
- The chat is a `/side` chat.

### Trust a hook

Installing a plugin trusts none of its hooks. The install preview lists them.

1. Open **Settings → Plugins** and select **Hooks** on the plugin. You can also run **Review Plugin Hooks…** from the command palette.
2. Read each hook. If Xum cut a long `input`, select **Show full input** first. **Trust** stays off until you do.
3. Select **Trust**. Select **Turn off** to stop a hook.

Xum trusts the exact definition of a hook: its event, its matcher, and its handler. Reformatting the file keeps trust. Trust lapses in these cases:

- The definition changes. The hook shows **changed, needs review** and does not run until you trust it again.
- The hook moves to another place in its file, for example to another group. It then shows **needs review**.
- You turn the hook off.
- You uninstall the plugin. A reinstall under the same name starts with no trusted hooks.

Xum checks trust before each hook call, not once per turn. A revoke stops the next call. A newly trusted hook starts to run on your next message.

### Events and handlers

| Codex event        | When Xum runs it              |
| ------------------ | ----------------------------- |
| `PreToolUse`       | Before a tool call            |
| `PostToolUse`      | After a tool call ran         |
| `UserPromptSubmit` | Before Xum sends your message |
| `Stop`             | When a turn finishes normally |

`Stop` does not run after an interrupted or failed turn, a compaction, a sub-agent turn, or a delegated workspace turn. It also does not run when a message or a wake is already queued when the turn ends, because the turn continues with that input.

Xum lists the other Codex events (`PermissionRequest`, `PreCompact`, `PostCompact`, `SubagentStart`, `SubagentStop`, `SessionStart`, `SessionEnd`, `Interrupt`) in Settings as "Never runs".

Xum runs only `mcp_tool` handlers. Such a handler calls `tool` on the plugin's own MCP server `server`. That server must be enabled and running in the workspace, or the hook does not run. Xum lists `command`, `prompt`, and `agent` handlers as "Never runs".

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "mcp_tool",
            "server": "guard",
            "tool": "check_command",
            "input": { "command": "${tool_input.command}", "cwd": "${cwd}" },
            "timeout": 5
          }
        ]
      }
    ]
  }
}
```

Xum fills `${field.path}` placeholders in `input` from the event fields below. A placeholder that is the whole string keeps its JSON type. A placeholder inside a longer string becomes text.

Within one plugin, matching hooks run one after another in file order. Plugins run in discovery order. `PostToolUse` runs in reverse plugin order. Codex-format hooks run before the [tool hooks](/hooks/tools) `.xum/tool_pre`, so `tool_pre` sees a rewritten input.

### Matchers

`UserPromptSubmit` and `Stop` ignore `matcher`. On tool events:

- `"*"`, `""`, `null`, or no matcher matches every tool.
- A list of names (letters, digits, `_`, and `|`, for example `Bash|Edit`) matches a whole name, not a substring.
- Any other value is a regex. Codex uses the Rust `regex` dialect. Xum compiles it as a JavaScript RegExp.
- A leading flag group of `i`, `m`, and `s` (for example `(?i)` or `(?is)`) becomes RegExp flags.
- Xum translates `(?P<name>...)` to a JavaScript named group, and the `\A` and `\z` anchors to lookarounds that mean the start and end of the name, as in Rust. A group name must follow Rust's rule and compile in JavaScript (letters, numbers, and `_`, at most 128 characters). A name used twice is refused.
- Xum refuses other Rust syntax that JavaScript reads in a different way or rejects. Examples are inline flags after the start, negated flags (`(?-i)`), the `x`, `U`, `u`, and `R` flags, `\pL`, `\p{...}`, `\x{...}`, `\b{start}`, `\<`, `\>`, nested or POSIX classes (`[[:alpha:]]`), and `&&`, `--`, or `~~` in a class.

Xum drops a group with a refused or invalid matcher and shows a warning in Settings. Xum tests the matcher against the Xum tool name and against the Codex name below.

### Timeouts

`timeout` is in whole seconds. The default is 10 seconds. Xum caps it at 30 seconds and raises `0` to 1 second. The Codex default of 600 seconds does not apply.

Before `UserPromptSubmit` hooks run, Xum waits for the workspace's MCP servers to start. The wait is at most the longest `UserPromptSubmit` timeout.

### Event fields

Every event has these fields:

| Field             | Value                                                      |
| ----------------- | ---------------------------------------------------------- |
| `hook_event_name` | `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, or `Stop` |
| `session_id`      | The Xum workspace ID                                       |
| `cwd`             | The workspace directory. See the note below the table.     |
| `permission_mode` | Always `bypassPermissions`. Xum asks for no tool approval. |
| `transcript_path` | Always `null`. Xum's chat log is not a Codex transcript.   |

Tool events always have `cwd`. On `UserPromptSubmit` and `Stop`, Xum leaves `cwd` out when it cannot resolve the workspace directory. A `${cwd}` placeholder then becomes `null` (whole string) or empty text (inside a longer string).

Per-event fields:

| Event              | Fields                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------- |
| `PreToolUse`       | `tool_use_id`, `turn_id`, `model`, `tool_name`, `tool_input`                                |
| `PostToolUse`      | The `PreToolUse` fields and `tool_response`                                                 |
| `UserPromptSubmit` | `prompt`. It has no `turn_id` and no `model`.                                               |
| `Stop`             | `turn_id` (the assistant message ID), `model`, `stop_hook_active`, `last_assistant_message` |

`last_assistant_message` is the reply's trailing text, after its last tool call, cut to its last 16,384 characters. It is `null` when the reply ends on a tool call or has no trailing text.

`model` is Xum's provider-qualified model string, for example `openai:gpt-5.2`. Codex sends the bare model name. A tool call outside a model turn has no `turn_id` and no `model`.

### Tool names and the Bash contract

| Xum tool                | `tool_name`             | `tool_input`       | `tool_response`            |
| ----------------------- | ----------------------- | ------------------ | -------------------------- |
| `bash`                  | `Bash`                  | `{ command }`      | The output text (a string) |
| An MCP tool             | `mcp__<server>__<tool>` | The tool arguments | The tool result            |
| Any other built-in tool | Its Xum name            | Its Xum arguments  | Its Xum result             |

A hook that reads `tool_input.script` does not work. Read `tool_input.command`. For a background `bash` call, `tool_response` is the output so far.

In an MCP name, Xum replaces each character other than `[A-Za-z0-9_]` with `_`. For the plugin's own server, `<server>` is the server name in the plugin.

### Outputs Xum honors

The hook's MCP tool returns its output as JSON text. Xum joins the text blocks of the result. If the result has no text, Xum reads `structuredContent`.

| Event              | Output                                                                                  | Effect                                                                                                                        |
| ------------------ | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `PreToolUse`       | `hookSpecificOutput.permissionDecision: "deny"`, or `decision: "block"`                 | Xum blocks the call. The model sees the reason as the tool error.                                                             |
| `PreToolUse`       | `hookSpecificOutput.permissionDecision: "allow"` with `hookSpecificOutput.updatedInput` | Xum runs the call with the new input.                                                                                         |
| `PostToolUse`      | `decision: "block"`, or `continue: false`                                               | Xum replaces the tool result with the hook's feedback.                                                                        |
| `UserPromptSubmit` | `decision: "block"` with `reason`, or `continue: false`                                 | Xum does not send a message you wrote. See the note below the table.                                                          |
| `UserPromptSubmit` | Plain text that does not start with `{` or `[`                                          | Xum adds the text as context.                                                                                                 |
| `Stop`             | `decision: "block"` with `reason`                                                       | The turn continues with `reason` as the next prompt, at most 3 times per message for each hook. See the note below the table. |
| `Stop`             | `continue: false`                                                                       | Xum ends the turn and shows `stopReason` to you.                                                                              |
| All but `Stop`     | `hookSpecificOutput.additionalContext`                                                  | Xum adds the text for the model. On tool events, it goes on the result as `hook_output`.                                      |
| Any event          | `systemMessage`                                                                         | Xum shows the message to you. The model never sees it.                                                                        |

A `UserPromptSubmit` block applies only to a message you send (typed, edited, queued, or plan-review feedback). Automatic sends (goal and task continuations, wakes, follow-ups) ignore every block, because their sender would retry the same message in a loop. They keep the context of the other hooks. A hook whose output both blocks and adds context loses its own context. The prompt that a `Stop` block queues is different: no `UserPromptSubmit` hook runs for it at all, as in Codex. A `UserPromptSubmit` guard cannot check it.

Each `Stop` hook continues one message at most 3 times, and all hooks together at most 50 times. When a hook continues the turn, Xum shows the notice "Plugin `<name>`: plugin continued turn n of 50". A newer notice replaces one that is still waiting to show, so a long loop does not queue 50 notices. Xum's own TODO and status nudges also count toward the 50, but show no notice. [Cursor hooks](#cursor-hooks) share these limits. For a turn that an ACP client or `xum run` owns, Xum runs the `Stop` hooks but never continues the turn. For a goal turn, Xum continues only while the goal can take another turn: not after it is paused or replaced, or after it reaches its turn, cost, or budget limit.

`hookSpecificOutput` must have `hookEventName` set to the event name. `Stop` has no `hookSpecificOutput`.

A rewrite in `updatedInput` must match the tool's input schema and pass the tool's own input parser (its refinements and defaults). If it does not, Xum denies the call. The tool runs with the parsed value. For `Bash`, set `updatedInput.command`. The call keeps its other Xum arguments.

The transcript keeps the model's original tool call. Xum adds a note to the tool result that names the fields the hook changed, for example `[plugin:guard] Rewrote this tool call's input (fields: script).` The note never contains the values, because a hook can put a secret into the input, and the model provider and the chat log see the note.

Xum honors an explicit deny or block when the rest of the output breaks a Codex rule, for example with an unknown field. It does not honor one when the output is malformed (a wrong type or a value outside an enum). See the list below. Xum does not support `permissionDecision: "ask"`, `updatedMCPToolOutput`, or `suppressOutput`.

### What fails open

In these cases, Xum logs a warning and continues without the hook's output:

- The hook times out, errors, or returns an MCP error.
- The server or tool is missing, disabled, or not running.
- The output is malformed: invalid JSON, a wrong type, or a value outside an enum. A deny or block in the same output is ignored too.
- The output has an unknown field. Xum then ignores the hook's other output, with two exceptions: on `PreToolUse`, `PostToolUse`, and `UserPromptSubmit` an explicit deny or block still applies, and a `PreToolUse` rewrite (`updatedInput`) makes Xum deny the call, because the hook allowed only its rewrite. On `Stop`, an unknown field voids the whole output, a block included. On every event, Xum still shows a `systemMessage` to you.
- The result text is over 1 MiB (1,048,576 characters).

One case fails closed. If the filled `input` of a `PreToolUse` hook is over 64 KiB (65,536 characters) as JSON, and the hook can run, Xum denies the call. A model can pad a command to get past a guard, so Xum does not let it through.

### Size limits

| Limit                                                                                                                  | Value             |
| ---------------------------------------------------------------------------------------------------------------------- | ----------------- |
| One text field of an output (`reason`, `permissionDecisionReason`, `stopReason`, `additionalContext`, `systemMessage`) | 16 KiB characters |
| Joined tool-event context or `PostToolUse` feedback of one plugin on one call                                          | 32 KiB characters |
| All `UserPromptSubmit` context on one message, as rendered for the model                                               | 64 KiB characters |
| One `hooks.json` file                                                                                                  | 256 KiB           |
| Hooks per plugin                                                                                                       | 256               |

Xum cuts the joined tool-event text at 32 KiB and adds `[plugin hook context cut]`. On `UserPromptSubmit`, Xum drops the context entries after the 64 KiB cap.

### Known gaps

- `PostToolUse` sees the MCP result after Xum's transform, not the raw MCP response. Xum removes protocol `_meta`, cuts large text, and converts binary content to Xum's `{ type: "content", value: [...] }` shape.
- `UserPromptSubmit` has no `turn_id` and no `model`.
- Only `bash` and MCP tools have Codex names. Hooks match file edits, `task`, and other tools by their Xum names.

## Cursor hooks

A [Cursor plugin](/agents/agent-skills#cursor-plugins) ships hooks in the [Cursor hooks format](https://cursor.com/docs/hooks): `hooks/hooks.json`, or the path or inline object of the `hooks` key in `.cursor-plugin/plugin.json`. Xum runs each `command` hook as a shell command. Xum runs three events and lists every other hook as "Never runs". The [size limits](#size-limits) for one `hooks.json` file and for hooks per plugin apply.

```json hooks/hooks.json
{
  "version": 1,
  "hooks": {
    "stop": [
      { "command": "\"${CURSOR_PLUGIN_ROOT}/hooks/stop-hook.sh\"", "timeout": 10, "loop_limit": 5 }
    ]
  }
}
```

### Where they run

Only managed plugins run Cursor hooks. Xum runs none in these cases:

- The project is not trusted.
- The workspace is not a local or worktree workspace, for example an SSH, Docker, devcontainer, or Coder workspace. Every Cursor hook shows "Does not run in remote workspaces (SSH, Docker and devcontainer)." Local multi-project workspaces do run them.
- The chat is a `/side` chat.
- `XUM_DISABLE_AGENT_TOOLS`, `XUM_DISABLE_TERMINALS`, or `XUM_DISABLE_PROJECT_AUTOMATION` is set to `1`.

<Warning>
  A Cursor hook runs as your OS user on the Xum host, with no sandbox. Trust only hooks whose
  commands and files you have read.
</Warning>

### Trust a hook

Trust works as for [Codex-format hooks](#trust-a-hook): select **Hooks** on the plugin, read each hook, and select **Trust**. If Xum cut a long entry, select **Show full entry** first. Xum trusts the entry exactly as declared, including fields that Xum does not use. A change to any field, or a move to another place in the list, asks for trust again. The panel shows each value as declared: a hook with `loop_limit: 80` shows 80 and stops at the ceiling of 50.

Trust covers the entry, not the scripts it runs. A hook can run any file in the plugin, so Xum reviews the files instead:

- When a plugin first has a hook that can run, the install preview lists every file of the plugin under **Files**, as `file <path> added`. An update that adds the plugin's first such hook lists every file among its changes.
- Later updates list each file that the update adds, changes, or removes.
- A UTF-8 text file of at most 64 KiB shows its text. A symlink shows its link text. Any other file shows only the row, with "(contents not shown: binary or larger than 64 KiB)".
- Xum marks invisible and bidi control characters in file paths, file texts, and the preview's warnings as `<U+XXXX>`, for example `<U+202E>`.
- If Xum cut a long text, Xum does not install or update the plugin until you select **Show full text** on it.
- A review too large to show fails with "This plugin's review is too large to show, so Xum cannot install or change it. Contact its publisher."

A file that changes on disk outside an update runs without a new review.

While no command hook of the plugin is trusted, the **Hooks** panel lists every file of the plugin under **Files**, and **Trust** stays off until you select **Show full text** on each cut text. If the files change before you trust the hook, Xum refuses with "This plugin's files changed since you reviewed them. Review them again."

### Events

| Cursor event         | When Xum runs it                                                             | Working folder     |
| -------------------- | ---------------------------------------------------------------------------- | ------------------ |
| `afterFileEdit`      | After a `file_edit_replace_string` or `file_edit_insert` call that succeeded | The plugin folder  |
| `afterAgentResponse` | When a turn finishes normally                                                | The plugin folder  |
| `stop`               | When a turn finishes normally, after the plugin's `afterAgentResponse` hooks | The workspace root |

`afterAgentResponse` and `stop` run when Codex `Stop` hooks run, with the same exceptions: not after an interrupted or failed turn, a compaction, a sub-agent turn, or a delegated workspace turn, and not when input is already queued. After a user Stop, no hook runs, and Xum kills a hook that is running. Edits through `bash` run no `afterFileEdit` hook.

These hooks never run, and the install review lists them under **Not applied in Xum**:

- A hook on any other event ("event not applied in Xum").
- A hook with a `matcher` ("matcher not applied in Xum").
- A hook with `type: "prompt"` ("prompt hooks are not applied in Xum").

A hook that Xum drops while it reads the hooks file, for example one without a `command` string or with a `loop_limit` that is not a whole number or `null`, also appears under **Not applied in Xum** with its reason. Xum lists at most 50 such hooks.

### The command

Xum runs `command` with `bash` through the workspace runtime, as written. On Windows that is Git Bash. Xum does not rewrite a leading `./`, so `./hooks/x.sh` in a `stop` hook looks in the workspace root, as in Cursor. Name the script from the plugin folder instead, as in the example above. `timeout` is in seconds: the default is 10 and the cap is 30, as for Codex-format hooks.

The process gets a minimal environment, not your shell's:

| Variable                                   | Value                                                                  |
| ------------------------------------------ | ---------------------------------------------------------------------- |
| `CURSOR_PROJECT_DIR`, `CLAUDE_PROJECT_DIR` | The workspace root                                                     |
| `CURSOR_PLUGIN_ROOT`                       | The plugin folder                                                      |
| `CURSOR_TRANSCRIPT_PATH`                   | The workspace's `chat.jsonl`. It is not in Cursor's transcript format. |
| `CURSOR_VERSION`                           | `xum-<version>`, not a Cursor version                                  |
| `PATH`, `HOME`                             | From the Xum process. Xum removes its own `bin` folder from `PATH`.    |

Xum also passes the same host variables as for a [plugin MCP server](/config/mcp-servers#plugin-server-environment), such as `USER`, `LANG`, `TMPDIR`, and the CA bundle paths, and the variables it sets for every command so that tools do not wait for input.

The input on stdin has these fields:

| Field             | Value                                                                                                                  |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `conversation_id` | The Xum workspace ID                                                                                                   |
| `generation_id`   | The turn ID, when there is one                                                                                         |
| `model`           | Xum's provider-qualified model string, when there is one                                                               |
| `hook_event_name` | The event                                                                                                              |
| `cursor_version`  | The same value as `CURSOR_VERSION`                                                                                     |
| `workspace_roots` | A list with the workspace root                                                                                         |
| `user_email`      | Always `null`                                                                                                          |
| `transcript_path` | The same value as `CURSOR_TRANSCRIPT_PATH`                                                                             |
| `text`            | `afterAgentResponse`: the reply text as in Codex `last_assistant_message` (see [Event fields](#event-fields)), or `""` |
| `status`          | `stop`: always `"completed"`                                                                                           |
| `loop_count`      | `stop`: the continuations of this user turn so far, from any hook or Xum nudge                                         |
| `file_path`       | `afterFileEdit`: the absolute path of the edited file                                                                  |
| `edits`           | `afterFileEdit`: `[{ old_string, new_string }]` from the tool input. An insert has an empty `old_string`.              |

### Output and failures

A `stop` hook can print `{ "followup_message": "..." }`. Xum then continues the turn with that text as the next prompt. Each `stop` hook continues one user turn at most 3 times. Set `loop_limit` to a whole number to change that, or to `null` for no limit of its own. All hooks together stop at 50 continuations per user turn, and your next message starts a new count. See the notice in [Outputs Xum honors](#outputs-xum-honors).

The other two events cannot change anything. Xum checks only that their output is valid. No Cursor event can block, so every failure fails open. Xum logs it, skips the hook's output, and shows "Plugin `<name>`: hook `<event>` failed (`<reason>`). Turn the hook off in Settings > Plugins." Xum shows that notice once per hook in each workspace. It shows the notice again after the set of trusted hooks that the workspace runs changes in any plugin (also when you remove the project's trust and restore it), after you archive and unarchive the workspace, or after Xum restarts.

| Result                                                  | Reason in the notice                                                                    |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Exit 0 with empty stdout                                | No failure                                                                              |
| Exit 0 with stdout that is not a JSON object            | `invalid output: not JSON` or `invalid output: not a JSON object`                       |
| A `stop` hook's `followup_message` that is not a string | `its followup_message is not a string`                                                  |
| Exit 2, or `permission: "deny"`                         | `exit code 2; this event cannot block`, or `permission "deny"; this event cannot block` |
| Exit 127                                                | `` `<command>`: a command or one of its dependencies was not found (exit 127) ``        |
| Another exit code                                       | `exit code <n>`                                                                         |
| No exit within the timeout                              | `timed out after <n>s`                                                                  |
| Stdout over 64 KiB                                      | `invalid output: over 65536 bytes`                                                      |
| Input over 64 KiB                                       | `its input is over 65536 characters`. Xum skips the call.                               |
| Xum cannot read its hook trust store                    | `Xum cannot read its hook trust store`. Xum skips the call.                             |

Other failures name their cause. Xum reads no stderr. Exit 127 means that the command, or a command it runs such as `jq`, was not found. `failClosed` has no effect on these events.

## Claude Code plugin hooks

A Claude Code plugin's `hooks/hooks.json`, and each file that the `hooks` key of `.claude-plugin/plugin.json` names, has the same shape as a Codex hooks file. Xum reads them and lists every hook in Settings as "Never runs", on every Claude Code event and for every handler type, `mcp_tool` included. Claude Code matchers name Claude Code tools, which Xum does not map. Xum warns about and ignores inline hooks objects in the manifest and `http` handlers.

## Xum-native hooks

A plugin can ship `hooks.js` in its root, or at the path that `contributes.hooks` in `plugin.json` names. Xum loads `hooks.js` from global plugins, and from project plugins in a trusted project. A package with only `.codex-plugin/plugin.json`, `.claude-plugin/plugin.json` or `.cursor-plugin/plugin.json` gets no `hooks.js`. Xum has no per-hook trust step for `hooks.js`. The install preview discloses it.

`hooks.js` is a script that evaluates to an object of hook functions. It runs in a QuickJS sandbox and cannot call tools. A function can be `async`. Each call has 5 seconds.

Tool hooks see only the tools that `plugin.json` lists in `extensions.mux.hooks.tools`. With no list, they see no tool. Tool hooks get Xum's tool names and arguments, for example `bash` and `args.script`.

```json plugin.json
{
  "extensions": { "mux": { "hooks": { "tools": ["bash"] } } }
}
```

```js hooks.js
({
  "tool.execute.before": (input) => {
    if (input.toolName === "bash" && input.args.script.includes("--force")) {
      return { deny: "Force flags are blocked." };
    }
  },
});
```

| Hook                  | Input                                                                      | Output                                                                          |
| --------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `tool.execute.before` | `toolName`, `args`, `workspaceId`, `cwd`, `settings`                       | `{ deny: "reason" }` blocks the call. `{ args: {...} }` replaces the arguments. |
| `tool.execute.after`  | `toolName`, `args`, `workspaceId`, `result` or `resultOmitted`, `settings` | `{ annotation: "text" }` adds the text to the result as `hook_output`.          |
| `request.assemble`    | `workspaceId`, `modelString`, `settings`                                   | `{ context: "text" }` adds the text to the system prompt.                       |

`settings` holds the structured settings (`openai/settings`) of the plugin's own connected MCP servers, keyed by server name. These fields tell a hook that Xum left out data:

- `settingsOmitted: true`: the settings JSON is over 64 KiB (65,536 UTF-8 bytes). The hook gets `settings: {}`.
- `resultOmitted: true`: the tool result is over 256 KiB (262,144 characters) as JSON, or Xum cannot serialize it as JSON. `tool.execute.after` gets no `result`.

A hook that crashes, times out, or returns a malformed output never breaks the turn. Xum logs it and continues. Xum ignores an `args` rewrite that is not an object. Xum drops `request.assemble` context over 64 KiB (65,536 characters). Xum adds an annotation only to an object result.
