Securely manage environment variables for your projects in Xum. Project secrets are automatically injected when the agent executes bash commands, making it easy to provide API keys, tokens, and other sensitive configuration.

![Project Secrets Modal](../img/project-secrets.webp)

## What Are Project Secrets?

Project secrets are key-value pairs stored per project that are:

- **Automatically injected** as environment variables when running bash commands
- **Stored outside repo** in `~/.xum/secrets.json`
- **Project-scoped** - each project has its own set of secrets
- **Workspace-inherited** - all workspaces in a project use the same secrets

## Common Use Cases

- **API Keys**: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GITHUB_TOKEN`
- **Authentication tokens**: `NPM_TOKEN`, `DOCKER_HUB_TOKEN`
- **Database credentials**: `DATABASE_URL`, `POSTGRES_PASSWORD`
- **Service endpoints**: `API_BASE_URL`, `WEBHOOK_URL`
- **Build configuration**: `BUILD_ENV`, `FEATURE_FLAGS`

## Managing Secrets

### Opening the Secrets Modal

1. Find your project in the left sidebar
2. Hover over the project name
3. Click the 🔑 key icon that appears

## How Secrets Are Used

When the agent runs bash commands (via the `bash` tool), all project secrets are automatically injected as environment variables:

```bash
# If you have a secret: GH_TOKEN=ghp_abc123
# The agent can use it in commands:
gh api /user  # Uses GH_TOKEN from environment
```

The agent doesn't need to explicitly reference secrets - they're available as regular environment variables in all bash executions within that project's workspaces.

## Provider keys in secrets

A secret replaces only the variable it sets. Bash commands in Local and Worktree workspaces still get every other variable from the environment that started Xum. A provider key in secrets can then mix with a base URL or token of the host:

| Secret              | Host variables that mix with it              |
| ------------------- | -------------------------------------------- |
| `ANTHROPIC_API_KEY` | `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN` |
| `OPENAI_API_KEY`    | `OPENAI_BASE_URL`, `OPENAI_API_BASE`         |

For example, on a host that starts Xum with an AI gateway in `ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN`, a secret `ANTHROPIC_API_KEY=sk-ant-…` goes to the gateway together with the gateway token. The gateway can answer 403. In the desktop app and `xum server`, Xum logs a warning for each workspace and provider with this mix (not in `xum run` and `xum workflow` sessions). The warning names the variables, never their values.

To avoid the mix, do one of these:

1. Remove the provider key from secrets, and let commands use the host's gateway.
2. Start Xum without the host's provider variables, so the key in secrets goes to the provider's own API.
3. Set in secrets every host variable from the table that the host sets, for example `ANTHROPIC_BASE_URL=https://api.anthropic.com`, or both `OPENAI_BASE_URL` and `OPENAI_API_BASE` as `https://api.openai.com/v1`. This does not work for a host `ANTHROPIC_AUTH_TOKEN`: the Settings page does not save a secret with an empty value, so use option 1 or 2 there.

A gateway token in secrets next to the host's gateway URL is a valid setup. Xum does not warn for it.

## Security Considerations

### Storage

- Secrets are stored in `~/.xum/secrets.json` (outside your repo)
- **Stored in plaintext** — the file is not encrypted
- The file is created with user-only permissions; treat it like any other credentials file
