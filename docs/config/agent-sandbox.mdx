---
title: Agent Sandbox
description: Run local agent commands in a macOS sandbox that keeps writes in the workspace and credentials out of reach
---

An agent runs shell commands with your user's rights. A wrong command can change files outside the workspace, read your keys, or send data to any host. The agent sandbox limits what agent commands can do. It is off by default.

The sandbox works only on macOS. It covers Local and Worktree workspaces. SSH, Coder, Docker, and Devcontainer workspaces are not covered: their commands run on another machine or in a container.

## Turn on the sandbox

In **Settings → Agents → Agent sandbox**, turn on **Run agent commands in a sandbox**. Commands that start after that run in the sandbox.

On another operating system, or on a Mac without `/usr/bin/sandbox-exec`, the section shows why the sandbox is not available and you cannot turn it on. If the setting is already on there (for example in a `config.json` copied from a Mac), the section says so, and you can only turn it off: with the switch, or with **Global** or **Off** for a project that is **On**. Until then:

- On another operating system, commands run without the sandbox.
- On a Mac without `sandbox-exec`, the commands that the sandbox covers fail. Xum does not run them without the sandbox that you turned on, unless you approve one command with **Run outside once** (see [Approve one command outside the sandbox](#approve-one-command-outside-the-sandbox)).

To use another setting for one project, select the project in **Project** and click:

- **Global**: the project follows the switch.
- **On**: the sandbox is on for this project, also when the switch is off.
- **Off**: the sandbox is off for this project, also when the switch is on.

A sub-project has the setting of its parent project, because its workspaces work in the parent's checkout. **Project** lists only parent projects, and Xum ignores an `agentSandbox` setting of a sub-project in `config.json`.

A multi-project workspace uses the strictest setting of its projects, because its commands can change each checkout. The sandbox is on when it is on for one of the projects. Commands can then use only the network mode, hosts, and extra paths that each project with the sandbox on allows.

Agent tools cannot change the sandbox setting.

## What commands can write

Commands in the sandbox can write only to these folders:

- The workspace and its scratch folder.
- Temp folders: `/private/tmp` and `$TMPDIR`. The sandbox sets `$TMPDIR` to the system temp folder, also when a secret sets it to another folder.
- Tool caches: `~/.npm`, `~/.cache`, `~/.cargo/registry`, `~/.cargo/git`, `~/go/pkg/mod`, `~/.gradle/caches`, `~/.m2/repository`, `~/Library/pnpm/store`, `~/.pnpm-store`, `~/Library/Caches/go-build`, `~/Library/Caches/pip`, `~/Library/Caches/Yarn`, `~/Library/Caches/ms-playwright`, `~/Library/Caches/node-gyp`, and `~/Library/Developer/Xcode/DerivedData`.
- For a worktree workspace, the `.git` folder of the main checkout, so that commits work.

A tool cache or `$TMPDIR` that is a symlink stays closed, because a command could replace it with a link to another folder. Add the folder that it links to to `extraWritePaths`.

If Xum's home folder (`~/.xum`, or `XUM_ROOT`) is inside a folder that commands can write, such as a temp folder, a tool cache or an `extraWritePaths` entry, commands in the sandbox fail to start, because a command could change Xum's own settings there.

Some files stay read-only, also inside the workspace and where they link to, because a command could use them to run code later outside the sandbox:

- `.git/hooks`, `.git/config`, `.git/config.worktree`, `.git/commondir`, `.git/modules` (the git folders of submodules), and `.git` itself where it is not a folder: the `.git` file of a worktree, or a `.git` that does not exist yet, so `git init` fails in the sandbox. In the `.git` folder of the main checkout, the same paths, and `config.worktree`, `modules` and `commondir` in the folder of each worktree.
- `.xum/mcp.jsonc`, `.mux/mcp.jsonc`, `.xum/mcp.local.jsonc`, `.mux/mcp.local.jsonc`, `.xum/mcp.local.json`, `.mux/mcp.local.json`, `.mcp.json`, `.xum/plugins`, `.mux/plugins`, and `.agents/plugins`.
- `.xum/tool_env` and `.mux/tool_env`, which bash runs before each command in a trusted project, also before a command that you let run outside the sandbox.
- `~/.npm/_npx`, the uv cache (`~/.cache/uv`, or where `XDG_CACHE_HOME` or `UV_CACHE_DIR` moves it), the Bun install and transpiler caches (`~/.bun/install/cache` and `~/Library/Caches/bun`, or where `BUN_INSTALL_CACHE_DIR`, `BUN_INSTALL`, `BUN_RUNTIME_TRANSPILER_CACHE_PATH` or `XDG_CACHE_HOME` moves them), and the `bunx-<uid>-*` and `.bunx-<uid>` folders in the temp folders. `npx`, `uvx` and `bunx` keep what they run there, also for MCP servers that start outside the sandbox. Commands in the sandbox can still run what is there. uv and Bun in the sandbox use caches of their own in `$TMPDIR`.
- `.vscode`, `.idea`, `.envrc`, and `.gitmodules`.
- `.devcontainer.json` and `.devcontainer`, because `devcontainer up` runs their `initializeCommand` on your Mac.

## What commands can read

Commands in the sandbox can read:

- The workspace and the folders they can write.
- System files and folders outside `/Users`, `/Volumes` and your home folder.
- Toolchains and tool settings in your home folder: `~/.gitconfig`, `~/.config/git`, `~/.bunfig.toml`, `~/.bun`, `~/.cargo`, `~/.rustup`, `~/go`, `~/Library/Application Support/go`, `~/.nvm`, `~/.volta`, `~/.pyenv`, `~/.asdf`, `~/.local/share/mise`, `~/.local/share/uv`, and `~/.sdkman`.
- The global skill and plugin folders.
- The folders in your `PATH` that are in your home folder. Only the folder itself opens: if a tool in it needs files next to it, add them to `extraReadPaths`. A `PATH` folder that a symlink in a writable folder links to stays closed.

Everything else in `/Users`, `/Volumes` and your home folder (also when it is not in `/Users`) is hidden. Some credential files stay hidden and read-only, also inside folders that are open and when you add them to `extraReadPaths` or `extraWritePaths`:

- `~/.cargo/credentials` and `~/.cargo/credentials.toml`.
- `~/.config/git/credentials`.
- `~/.cache/huggingface/token`.
- Xum's `server.lock`, `providers.jsonc`, `secrets.json`, `mcp-oauth.json`, and `config.json`, and its `askpass` folder, where your answers to SSH prompts pass.

These files are not open, because they can hold tokens: `~/.npmrc`, `~/.pypirc`, `~/.gradle/gradle.properties`, and `~/.m2/settings.xml`. If a build needs one of them, add it to `extraReadPaths` (see [Open more paths](#open-more-paths)).

Unix sockets are closed in all network modes, for example the sockets of Docker, `ssh-agent`, 1Password, and `gpg-agent`. The macOS keychain is closed too.

## Network

Commands in the sandbox reach the network through a local proxy. In **Network**, select one mode:

- **Allowed hosts only** (the default): commands can reach only the hosts in the list. The default list has 16 package registries and git hosts: `registry.npmjs.org`, `registry.yarnpkg.com`, `pypi.org`, `files.pythonhosted.org`, `crates.io`, `index.crates.io`, `static.crates.io`, `proxy.golang.org`, `sum.golang.org`, `github.com`, `api.github.com`, `codeload.github.com`, `objects.githubusercontent.com`, `raw.githubusercontent.com`, `gitlab.com`, and `bitbucket.org`.
- **Any host**: commands can reach all hosts.
- **Loopback only**: commands can reach only `localhost`.

To change the list, click **Edit hosts**, enter one host on each line, and click **Save hosts**. To go back to the default list, click **Edit hosts**, then **Use defaults**. A list that you edited does not change when a later version of Xum changes the default list.

In all modes, loopback stays open, so dev servers and their tests work. The proxy refuses an allowed host name that resolves to a private address range.

## Open more paths

To let commands write or read more paths, edit `~/.xum/config.json`:

```jsonc
{
  "agentSandbox": {
    "enabled": true,
    "network": "allowlist",
    // Folders that commands can write and read.
    "extraWritePaths": ["~/.gradle"],
    // Files and folders that commands can read.
    "extraReadPaths": ["~/.npmrc"],
  },
}
```

A path can start with `~/`. A project can have its own `agentSandbox` with the same fields, in its entry in `projects`. Each field that the project sets replaces the global field. For example, a project `extraReadPaths` replaces the global `extraReadPaths`, it does not add to it. A repository cannot set the sandbox. The agent's config tool cannot change `agentSandbox`, and while the sandbox is on, it cannot change `projects`: it cannot add, remove or trust a project, or add or change a workspace.

Xum ignores a field that is not valid and keeps the valid fields, so a broken field next to `"enabled": true` does not turn the sandbox off. An `agentSandbox` value that is not an object is ignored as a whole. Xum shows no message for this, and the next save from Settings writes the value without the broken fields.

## Approve one command outside the sandbox

When the sandbox blocks a command, the bash card shows a **Sandbox** badge and a line that names what the sandbox blocked. The agent can then ask to run the command once outside the sandbox, with a reason.

The request shows as a card with the command and the reason. Click **Run outside once** to run that one call without the sandbox, or **Deny** to refuse it. The keyboard shortcuts answer the newest card (see [Keyboard shortcuts](/config/keybinds)).

Each approval applies to one call. Xum never remembers it. Headless `xum run`, `xum workflow`, and ACP clients refuse such requests at once.

An approved call starts without `BASH_ENV`, as do MCP servers and the commands that Xum runs for itself while the sandbox is on, because a sandboxed command can change the file that it names. The commands that Xum runs for itself also use `/bin/bash` and the system folders in place of your `PATH`, because a folder in your `PATH`, such as an activated `.venv/bin`, can be in the workspace.

<Warning>
  An approved command runs with full access to your files, keys, and network. It could read the Xum
  server token, answer later approval cards, or turn the sandbox off. It also runs what it finds in
  the workspace, which sandboxed commands can change: a script, a git hook in the workspace, or a
  file that `NODE_OPTIONS` or `PYTHONPATH` names. Approve only commands that you read and trust.
</Warning>

## Known limits

- Programs with a sandbox of their own, such as Chrome, Electron, Playwright, Codex, and Claude Code, cannot start it inside the agent sandbox. Start them with their no-sandbox flag. Codex and Claude Code also need their login folders in `extraReadPaths`.
- `git push` over SSH fails, because the `ssh-agent` socket and the SSH keys are closed. `gh` with a stored login fails, because the keychain is closed. Approve the one push outside the sandbox.
- A commit or `git submodule update` that changes the git folder of a submodule fails, because that folder is read-only. Approve the command outside the sandbox.
- File tools check the real path of a file and then open it. A sandboxed command that swaps a symlink between the check and the open can make a file tool read or edit a file that the sandbox hides.
- The VS Code extension shows no approval card yet. A request to run a command outside the sandbox waits there until you stop the agent.
- Project secrets and the bash AI proxy key are still in the environment of agent commands.
- The sandbox does not cover terminals that you open, MCP servers (they start outside the sandbox), and the Browser tab.
- Commands can change the other files in the workspace. When you, your editor, or a Dev Container later runs one of them outside the sandbox, for example a script that `initializeCommand` names or a Dev Container config in another folder, the change runs with your full access.
- Tool caches, temp folders and the workspace are writable, so a command can change a package that a program outside the sandbox runs later, for example a build in your terminal, or an MCP server that `npx` or `bunx` finds in the `node_modules` folder of the workspace or gets from a registry that a `.npmrc`, `bunfig.toml` or `uv.toml` in the workspace names.
- With Bun 1.4.3 or older, `bunx` fails in the sandbox, because it keeps what it runs in `/private/tmp`, where that stays read-only. Update Bun, or approve the call outside the sandbox.
